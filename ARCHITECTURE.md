# AgriVision Architecture

## Phase 1 — Offline-first Farm Operations

AgriVision uses Room as the planned local source of truth for structured farm data.

Core domain:
- Farm
- Livestock
- Crops
- Feed logs
- Production
- Expenses
- Sales
- Inventory

Operational relationship:

`Farm → Livestock/Crops → Feed & Production → Expenses/Sales → Inventory → Dashboard → Reports`

## Data rules

Every operational record carries a `farmId` so the model is multi-farm ready.

Records use stable string IDs generated by the repository layer. Dates are stored as ISO-style text (`yyyy-MM-dd`) for predictable local filtering and reporting.

Dashboard metrics are calculated from database queries instead of hard-coded totals.

## Room layer

The current repository contains:
- `FarmEntities.kt` — Room entities
- `FarmDao.kt` — reactive queries and writes
- `AgriDatabase.kt` — singleton Room database
- `FarmRepository.kt` — application-facing data operations

Room 2.8.5 is used for the current stable offline database layer.

## Migration strategy

Existing SharedPreferences records are kept temporarily while UI screens are migrated.

Next migration steps:
1. Make Room the source of truth for Farm and Livestock.
2. Move Crops and Inventory to Room.
3. Add Feed Log UI and persistence.
4. Move Production, Expenses and Sales to Room.
5. Replace dashboard calculations with Room Flow queries.
6. Move Reports and backup/restore to Room-backed exports.
7. Retain field incidents, assistance and audit history as first-class Room tables.

This staged migration avoids breaking the working prototype while the persistence layer is replaced.

## Government workflow layer

The DA-oriented workflow remains separate from basic farm operations:

`FARMER → FIELD EVENT → EVIDENCE → VALIDATION → ASSISTANCE → OUTCOME`

Official DA transmission is not assumed. A connected, authenticated and authorized backend will be a later integration phase.
